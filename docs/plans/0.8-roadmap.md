# toolmenu 0.8 → 0.11: plan

Status: revised after an independent review (section 10 lists what changed and
why). Nothing here is built yet.

Where this comes from: running toolmenu on 25 public MCP servers (FINDINGS F12,
2026-09-28). What held up: `diff` (every breaking change it reported was real, after
the `anyOf` fix) and the second-process check (it found mcp-atlassian's
per-process menu). What didn't: token counts (fixed in 0.7.1), the naming and ID
heuristics (noisy on good servers), and `session`'s scripted unlock check, which had
nothing to find on servers that don't unlock tools, and needs a hand-written
scenario before it finds anything at all.

The six points, in build order. Each ships on its own.

| # | Point | Command | Release |
|---|---|---|---|
| 1 | Pinned hash seed + cross-process determinism + quieter heuristics | `snapshot` | 0.8.0 |
| 2b | Setup-problem detection (auth, missing dependencies) | `session` | 0.8.0 |
| 6 | Servers behind OAuth | all | 0.9.0 |
| 2a | `session --auto`, minimal: unlock phase + schema-derived arguments | `session` | 0.9.0 |
| 3 | The union menu (every tool a session saw), diffed like any menu | `session` | 0.9.0 |
| 5 | Where the tokens go + the schema rules the corpus supports | `snapshot` | 0.10.0 |
| 4 | Connection matrix, identities, corrected cache wording | `session` | 0.10.0 |

Cross-cutting work (section 7) comes first: a reproducible corpus, so every change
below is measured against the same servers instead of argued about. **Before 2a and
3, the corpus needs servers that actually unlock tools** (none of the 25 do): kh-mcp
(private, run locally, results not published) and GitHub's server if its current
flags still offer dynamic toolsets.

---

## 0. Principles that constrain every point

- **No LLM, deterministic.** Same inputs, same output (README).
- **A rule ships only if it points to a real failure** (README: "If a rule can't point
  to one, it doesn't ship"). For the new rules that means: it fires on at least one
  corpus server, and every corpus hit was checked by hand.
- **Precision over recall for anything at `warn` or `error`.** A first run on a good
  server should be quiet. Heuristics default to `info`.
- **Never call a tool that isn't `readOnlyHint: true` without `allow_writes`**, and
  never in `--auto` mode at all.
- **Menu file format stays `toolmenu: 1`.** The union menu (point 3) is an ordinary
  menu file; there's no new file format.

## 1. `snapshot`: cross-process determinism, and quieter heuristics

### 1a. Check more than one process (or connection)

**Problem.** `menu/nondeterministic` lists twice on one connection. mcp-atlassian's
menu is stable within a process and different in every new one (a Python `set`
joined into a default). Only `session` caught it, because it happens to start a
second process.

**Design.**
- New module `src/probe.ts`, shared by `snapshot` and `session`:
  `probeMenus(target, { count, seeds, timeoutMs }) → Menu[]`. Starts `count` fresh
  processes (stdio) or connections (HTTP), lists each once, closes.
  `session`'s existing `freshMenu` and connection-variance check move onto it.
- **stdio: pin the seed on the main process, vary it on the probe.** The main
  process (the menu that gets saved and diffed) always runs with `PYTHONHASHSEED=0`
  unless the user set it with `--env`. That makes a Python server's saved menu
  reproducible: today mcp-atlassian's menu changes on every run, so every Action PR
  and every `history` step on it gets `diff/schema-other` noise. The probe process
  gets `PYTHONHASHSEED=1`, which turns the ordering bug into a difference every run.
  - What the seed covers: `str`/`bytes` hashing, so the order of sets and frozensets
    of strings (and of dicts built from them). Dicts keep insertion order otherwise.
  - What it doesn't: Go maps and Rust `HashMap` are randomized per process with no
    env var. A menu built once at startup from a map is stable within a process and
    different across processes, so only the second process catches it, by chance
    (likely for anything over a few items). The finding says which case it is.
  - Servers started through a wrapper that drops the environment (`docker run -i`
    without `-e`) don't get the seed. Detect a command starting with `docker`/
    `podman` and say the seed wasn't applied.
- **HTTP:** `count` fresh connections with the same headers.
- New rule **`menu/process-variance`** (stdio) / **`menu/connection-variance`**
  (HTTP), severity `error`, like `menu/nondeterministic`: every restart or client
  gets bytes that can't reuse a cached prefix. HTTP retries once before reporting
  (a rolling deploy can serve two versions for a moment).
- **One severity for one condition.** `session/connection-variance` on stdio is a
  `warn` today (session.ts); it becomes the same rule and severity as snapshot's.
  Test `http: menus that differ per connection…` and the stdio case are updated.
- **Session's scope probe must use the main process's seed**, not the probe's:
  `scopeOf` compares a fresh process with the changed menu, and a different seed
  would leak ordering variance into every scope verdict.
- **The detail says what differs, down to the value**, via a new helper
  `firstDifference(a, b) → { path, before, after }` (JSON path of the first differing
  leaf): `jira_get_issue.inputSchema.properties.fields.default: "assignee,descr…" vs
  "issuetype,assign…"`. Also used by `menu/nondeterministic` and `session/edit`,
  which today only say "inputSchema changed".
- **Same-content detection:** if the two values are permutations of the same
  comma-separated list or array (enums included), say so ("same 11 items, different
  order: sort them"). Key-order-only changes (`serialization`) have no differing
  leaf; they get their own message.

**Surface.** `--processes <n>` (default 2: the main one plus one probe; `1` turns
the probe off); config `processes`. `history` uses 1, seeded.

**Cost.** One extra server start per snapshot.

**Tests.** A fixture server that orders a default by `process.env.PYTHONHASHSEED`
(deterministic per seed), one that is stable, and one that is random per process
without the env var (caught by chance with 3 processes; the test asserts on the
seeded one only). Unit tests for `firstDifference` and the permutation check.

**Corpus check.** Must flag mcp-atlassian 0.23.1, and nothing else among the 22
servers that ran (none showed variance in F12).

### 1b. Heuristics that stop crying wolf

What F12 showed, and the change for each:

| Rule | False alarm on the corpus | Change |
|---|---|---|
| `naming/vague-id` | GitHub's `ref` (a git ref) ×4 | Drop `ref` from the vague list; keep `id`, `ids`, `uuid`, `identifier` |
| `ids/authored` | Figma `nodeId` ("often found as URL parameter node-id") | Provenance phrases gain "found in/as … URL", "URL parameter". Not a bare mention of "URL": Sentry's "Required when not using a URL" names an alternative input, and a loose match would pass it by accident |
| `ids/authored` | chrome-devtools `insightSetId`, `serviceWorkerId`: returned in another tool's text output | No reliable static signal. Default severity → `info`, message says so |
| `ids/authored` | Miro ×34: 17 are `orgId` ("org" never matches the `get-organization-*` tools), 1 is `parentId` (a single-word qualifier becomes the kind) | Abbreviation map (org↔organization, repo↔repository, …); a lone qualifier means no kind. Findings grouped per kind (34 → about 7) |
| unlock detection (`--init`) | `category`/`categories` on search tools (GitHub, Firecrawl) | Weak parameter names (`category`, `group`, `feature`, `module`) need a second signal (name or description); strong ones (`toolset`, `domain`) don't |

- **Severity defaults:** `ids/authored` `warn` → `info` (kept, not removed). `naming/vague-id` stays
  `warn` (narrower list). Config can raise both.
- **Measured:** before/after counts on the corpus go in FINDINGS (as F7 did).

## 2. `session --auto`: explore without a scenario, and say when nothing was tested

**2b ships first (0.8.0); 2a is minimal (0.9.0).** Measured on the corpus: 262 of
606 tools are read-only, six servers have none (Miro, Brave, Browserbase, Tavily,
jira-aashari, the archived GitHub server), and of the 262 only 39 need no arguments
(already covered by `--init`) and 43 more can be filled from the schema. 113 need
values like GitHub's `owner`/`repo` or Jira's `issue_key` that no schema or ID
harvest supplies. So `--auto`'s real value is the **unlock phase**, and argument
synthesis is a supporting act.

### 2a. Automatic exploration (minimal first)

Build now: steps 1, 2 (const/default/enum/type only), 4, 5, 6, 7 below.
Deferred until the corpus shows it would reach tools: step 3 (harvesting).

**Problem.** `session` needs a scenario, and the starter one only calls read-only
tools with no required arguments. On the corpus, most read-only tools need
arguments, so most of each menu was never exercised.

**Design.** `session --auto` builds the steps as it goes:

1. **Order:** tools with no required arguments first; then collection lookups
   (`list_*`, `search_*`, `find_*`); then single lookups (`get_*`); then everything
   else that's read-only. Unlock candidates (1b's stricter detection) get their own
   phase (below).
2. **Arguments from the schema** (`src/args.ts`, `synthesize(schema, pool)`), for
   required properties only, in this order:
   `const` → `default` → first of `examples` → first `enum` value →
   **a harvested value** (below) → by type: boolean `false`; integer/number:
   `minimum` or `1`; string by `format`: `date-time`/`date` (fixed dates, not "now":
   determinism), `uri` → `https://example.com`, `email` → `user@example.com`; string
   named `query`/`q`/`search`/`text` → `"test"`. Arrays: one synthesized item.
   Anything else (a `pattern`, an ID with nothing harvested, a nested object with
   required fields it can't fill) → the tool is **skipped with the reason**, never
   called with junk.
3. **Harvesting IDs.** Every successful result (`structuredContent`, or text that
   parses as JSON) is walked for keys like `*_id`, `*Id`, `id` (with the parent key as
   the kind: `issues[].id` → issue). Values go into a pool keyed by kind. A later
   `get_issue(issue_id)` gets a real ID. That's what lets `--auto` reach past the
   list tools.
4. **Unlock phase.** For each unlock candidate: call it with each enum value (cap 5),
   list after each, then call the first value again (it should change nothing).
   Servers that declare `listChanged: true` get this phase even without a name
   signal, for tools with an enum parameter.
5. **Budgets:** `--max-calls` (default 40), one call per tool outside the unlock phase,
   the usual per-request timeout, and a total time budget (default 5 min).
6. **Safety:** only `readOnlyHint: true`, always; `allow_writes` doesn't apply to
   `--auto`. `readOnlyHint` is the server's own claim, not a guarantee the call is
   free: `query: "test"` spends credits on Brave, Exa, Tavily, Firecrawl and Apify.
   So:
   - tools whose `openWorldHint` isn't `false` are **skipped unless `--open-world`**;
   - a per-server call budget (`--max-calls`, default 20);
   - the report and the saved scenario record argument *names* and synthesized
     values only; anything taken from a server's responses (harvested values, when
     that lands) is replaced with a placeholder unless `--keep-values`.
   The docs say plainly: `--auto` calls real APIs with your credentials.
7. **Output:** the usual session report, plus the **scenario it ran**
   (`--save-scenario <path>`): the concrete steps with the arguments used, so the
   run can be committed and replayed as a normal scenario.

The Action gets `scenario: auto`.

**Tests.** A fixture server with a list/get pair (IDs in `structuredContent`), a tool
with an unfillable pattern (skipped), an unlocker with an enum, a non-read-only tool
(never called), an open-world tool.

**Corpus check.** Calls made per server, tools reached (with and without harvesting),
and anything found. With dummy keys most calls will fail on auth (2b); the number
that matters is how many tools got a well-formed call.

### 2b. Tell setup problems apart from findings

**Problem.** With dummy keys, GitHub's run ended in `session/step-failed` (an error,
exit 1) and a stack of `session/tool-error` warnings. None of it was about the menu.

**Design.**
- Classify every failed call (protocol error or `isError` result) by its text and
  code, with patterns taken from the corpus's real messages, one classifier shared
  with the Action's missing-secret check (run.sh):
  - `auth`: 401/403, "unauthorized", "bad credentials", "invalid api key",
    "token expired", "invalid token" (not a bare "token"); also a 404 on a call
    that needs no ID, which is how some APIs answer a bad token (HubSpot
    `get-user-details`).
  - `environment`: the server lacks something on this machine ("Could not find
    Google Chrome executable", "not found at /opt/google/chrome": Chrome
    DevTools, Playwright).
  - `invalid-arguments`: JSON-RPC `-32602`, "validation", "either … or …", "is
    required".
  - `network`: ECONNREFUSED, DNS, timeouts.
  - `other`, including a bare "HTTPError" (Atlassian).
- **`auth`, `environment`, `network`:** no per-step error. One finding,
  **`session/untested`**: "6 of 9 calls failed on authentication, so those steps tested nothing
  after a successful call. Run with real credentials: `--env GITHUB_TOKEN=…`." The
  step still lists the menu afterwards (a failed call can change it).
- **`invalid-arguments` in `--auto`:** the synthesized arguments were wrong. Reported
  in the step note, not as a finding.
- **`other`:** as today (`session/tool-error` / `session/step-failed`).
- **Severity:** `warn` when some calls worked; **`error` when every call failed
  that way**. Otherwise an expired CI secret turns the job green while testing
  nothing (`history` already fails when every version failed).

## 3. The union menu: every tool a session saw, diffed like any menu

**Problem.** `diff` compares one menu per release. On a server that unlocks tools,
the saved menu holds the core tools only, so the tools behind unlocks are never
diffed (kh-mcp's review: 18 of 115 tools).

**Design (the smallest version that solves it).**
- `session --union-out menu.json` writes every tool the session saw, in the order
  first seen, as an ordinary `toolmenu: 1` menu file (`server` and protocol from
  the main connection).
- That file is the baseline: `diff` compares it across releases with every existing
  rule, so a breaking change in a tool that only exists after an unlock is caught.
- The Action: with `scenario` set, `union-out` becomes the menu it diffs
  (`baseline-from: session`), so a gated server needs one Action step, not the
  two-step recipe in docs/github-action.md.

**What it doesn't cover:** *how* a step changes the menu (append vs insert, scope,
announcements) between releases. `session` already reports those against the rules
on every run, which covers regressions in CI. Full trace diffing comes back only if
the union menu turns out not to be enough on the unlocking servers in the corpus.

**Tests.** A session fixture with two unlocks: the union holds core + both sets;
`diff` between two fixture versions reports a breaking change in an unlocked tool.

## 4. Session connection matrix, and accurate cache wording

### 4a. Who sees which menu

- **`--connections <n>` / `--processes <n>`** (from 1's `probe.ts`) instead of
  today's fixed second connection.
- **Identities (last; needs two real credentials to test):** `--as <name>` groups of `--header`/`--env` (e.g. `--as alice
  --header "Authorization: Bearer $A" --as bob --header "Authorization: Bearer $B"`;
  config: `identities: { alice: { headers: {…} }, … }`). Each identity gets a
  baseline menu.
  - **`session/caller-variance`** (info): the menu depends on who asks. Allowed by
    every protocol version; worth knowing.
  - Combined with `cacheScope`: menus differ by caller **and** the list says
    `cacheScope: "public"` → **`spec/cache-scope`** (error): a shared cache would
    serve one caller's menu to another. Menus identical and `private` → info
    (could be `public`).
- **Over time:** `--relist-after <ms>` lists again after a wait on an idle
  connection: **`session/time-variance`** (warn). Catches menus driven by
  remote config or expiring state. Off by default (it's a wait).

### 4b. Say what a change costs, accurately (smaller than first planned)

The first draft proposed a cost model ("re-processes from position p"). It
contradicted SPEC §20: per Claude's docs, adding, removing or reordering a tool
invalidates the entire cache, and in real clients a server's tools don't start at
position 0 (built-in tools and other servers come first). A user-supplied
conversation size would also dominate every number: false precision.

So instead:
- **Fix today's wording.** Cache findings currently say "~N tokens of the tool list
  from position p on … a floor". Replace with what's documented: any change to the
  tool list invalidates the cached prompt, the whole tool list and everything after
  it are processed again; the finding gives the size of this server's menu as the
  part toolmenu can measure.
- **Client note, not a model.** `--client tool-search` changes `session/append` to
  `info` with a note that deferred loading avoids the rebuild only if the client
  appends tools after the cached content, and that this depends on the client:
  toolmenu can't verify it. No totals.

## 5. `snapshot`: where the tokens go, and schema rules from real data

### 5a. Token breakdown

A section in the snapshot report (all formats; not findings unless noted):
- Top tools by tokens with their share ("`get_file_contents` 8% · top 5 = 31%").
- Per tool: description vs input schema tokens.
- **Largest enums** (values, tokens).
- **Repeated sub-schemas:** property schemas (canonical JSON, ≥ 50 tokens) that
  appear in 3+ tools, with the total ("`owner`+`repo` pair: 41 tools, ~1,900
  tokens").
- One info rule, **`size/dominant-tool`** (one tool over 30% of a menu of 5+
  tools): Brave's `brave_place_search` (68%) and Tavily's `tavily_search` (37%) on
  the corpus. `size/large-enum` doesn't ship as a rule (one server); the largest
  enums are listed in the breakdown instead.

### 5b. Schema rules

Each is checked against the corpus before it ships (principle in 0).

| Rule | What | Severity | Seen in |
|---|---|---|---|
| `schema/undescribed` | Parameters without a description (one summary finding per server) | info | 264 of 2,489 parameters |

Measured on the corpus and not shipping: `schema/unresolved-ref` and

## 6. Servers behind OAuth

**Problem.** The official remote servers (GitHub's hosted one, Atlassian, Sentry,
Figma, Miro, Linear…) require OAuth. toolmenu can check them only with a static
header today, and most don't issue static tokens.

**Design.**
- `toolmenu auth login <url>`: an `OAuthClientProvider` (the SDK's interface) with:
  - **Client registration:** Client ID Metadata Document if the server supports it,
    else dynamic registration, else `--client-id`/`--client-secret` for a
    pre-registered app.
  - **Redirect:** a loopback server on a **fixed** port (`127.0.0.1:33418/callback`,
    `--port` to change): dynamic registration records the exact redirect URI, so a
    random port would invalidate stored client information on the next login. If
    the port changes, toolmenu registers again. The authorization URL is printed
    and opened (best effort). `state` is generated and checked by toolmenu (the
    SDK's `finishAuth` checks `iss`, not `state`); PKCE and the token exchange are
    the SDK's. `finishAuth` runs on the transport that started the flow, which then
    reconnects.
  - **Client ID Metadata Document:** needs a metadata document at a stable HTTPS
    URL listing loopback redirects, and any local app can present that client ID.
    Not in the first version: dynamic registration and pre-registered clients
    first; CIMD only if a server in the target list requires it.
  - **Scopes:** the server's advertised defaults, or `--scope`.
- **Token store:** `~/.config/toolmenu/auth/<sha256(origin+path)>.json`, mode `0600`,
  recording the authorization server's `issuer` (the SDK passes it) and checking it
  on reuse,
  holding client information and tokens (with refresh). `auth list`, `auth logout
  <url>`. Tokens are never printed or written to reports.
- **Every command** (`snapshot`, `session`, `diff` doesn't connect) uses stored
  tokens for an HTTP target automatically when present (`--no-auth` to skip);
  `session`'s extra connections reuse the same provider, so one login covers them.
  A 401 with no stored tokens says: "run `toolmenu auth login <url>`".
- **CI:** a browser can't run there. Documented options: a static token as a
  header (unchanged), or `--client-credentials` (the SDK's
  `ClientCredentialsProvider`) where the server supports machine clients.
- `usedAuth` (for `spec/cache-hints`) is true with OAuth.

**Tests.** A fixture authorization server (metadata, registration, authorize with
auto-approve, token, refresh) in front of an MCP fixture guarded by the server SDK's
`requireBearerAuth`. End to end: login, snapshot with the stored token, expired
token → refresh, revoked → the "log in" message.

**Manual validation** needs real accounts: GitHub, Atlassian and Sentry remote
servers, run by the maintainer.

**Risks.** Servers differ in which registration methods they accept; some remote
servers allow only allow-listed clients. The plan is to support the three methods
above and report clearly which one a server refused.

## 10. What the review changed

An independent review checked this plan against the code, the SDK and the corpus.
Accepted:
- Pin the hash seed on the main process (the bigger win than varying it); Go/Rust
  maps vary per process with no env var; wrappers like `docker run` drop the seed.
- The scope probe must share the main process's seed; stdio variance gets one
  severity across `snapshot` and `session`.
- `--auto` reaches about 31% of read-only tools at best on the corpus, none on six
  servers: minimal version, unlock phase first, harvesting deferred.
- `--auto` safety: open-world opt-in, call budget, no response data in saved files.
- The 2b classifier rebuilt on the corpus's real error texts; all-auth-failed is an
  error, not a green job.
- The cost model contradicted SPEC §20; replaced with corrected wording.
- Two of four schema rules had zero hits; one is a generator artifact. Dropped.
- Full traces replaced by the union menu.
- OAuth: fixed port, `state` checked by toolmenu, CIMD deferred, issuer recorded.
