# toolmenu 0.15 → 0.19: the 2026-07-28 standard, and what the scans found

Status: decided (section 10). 0.15.0 landed the open work; 0.16.0 builds points 1–3. Points 4–8 not built yet.

Where this comes from: a scan on 2026-10-31 of ~235 servers (186 recent npm and
PyPI servers from the official MCP registry, plus the 60 most-downloaded npm MCP
packages). 144 gave a menu, and **42 of those (29%) already speak 2026-07-28**.
Each change below is checked against the 2026-07-28 changelog
(`docs/specification/2026-07-28/changelog.mdx`), and against the bundled
`schemas/2026-07-28.json` where it says more.

**Direction: new protocol work targets 2026-07-28 only.** Roots, Sampling and Logging
are deprecated there (SEP-2577) and are not built. Earlier versions keep the support
they have.

## 0. Principles, and what's new

The 0.8 plan's principles hold (no LLM, precision over recall at `warn`/`error`,
never call a tool that isn't `readOnlyHint: true` without `allow_writes`, menu
format `toolmenu: 1`). Two more:

- **Spec-traced rules.** Points 1–3 come from the 2026-07-28 spec, not from the
  article the identity rule (SPEC §1) names. SPEC §1 now says a rule also earns its
  place when a **2026-07-28 MUST makes compliant clients hide, reject or misread part
  of the menu**. That is still "observe the menu": the menu as clients show it, not
  as the server sends it (decision 1, §10).
- **Corpus hits, or tests that show the behaviour (decision 2).** The 0.8 rule is
  "fires on at least one corpus server, every hit checked by hand". Some 2026
  features aren't in the wild yet: 0 network `$ref`s in 144 menus, and 1
  `x-mcp-header`, on the reference server. A spec-traced rule with no corpus case
  ships when its tests show the behaviour end to end:
  - a fixture server for each way the rule fires, and one for each way it must stay
    quiet;
  - the run through the CLI, checking the finding, its severity, its message and its
    next step.

  Unit tests of a helper alone don't count.

## 1. Multi round-trip requests in `session`

**Problem.** In 2026-07-28 a tool that needs input returns an `InputRequiredResult`
(`resultType: "input_required"`, with `inputRequests` and/or `requestState`), and
the client calls the tool again with `inputResponses` (SEP-2322, changelog major 7).
The SDK client toolmenu uses rejects that result unless the caller opts in
(`allowInputRequired` / `inputRequired.autoFulfill`), and toolmenu doesn't. So
`session` reports every 2026 tool that asks for input as a failed call: a false
error, like `server-everything`'s `get-roots-list` was on 2025.

**Spec basis.**
- Results carry `resultType`; "Servers implementing this protocol version MUST
  include this field" (schema, `InputRequiredResult.resultType`; changelog major 8).
- Capabilities are declared per request in `_meta`
  (`io.modelcontextprotocol/clientCapabilities`, "Required"; "Servers MUST NOT infer
  capabilities from prior requests").
- `MissingRequiredClientCapabilityError`: code `-32021`, `data.requiredCapabilities`.
- Elicitation answers: `accept`, `decline`, `cancel` (`ElicitResult.action`).
  "Servers MUST NOT send elicitation requests with modes that are not supported by
  the client" (`client/elicitation.mdx`).

**Design.**
- On a 2026-07-28 connection, every request declares
  `clientCapabilities: { elicitation: { form: {}, url: {} } }`. Not roots, not sampling.
- Call tools with `allowInputRequired: true`, so toolmenu sees the raw
  `InputRequiredResult` and drives the retries itself (observable, deterministic).
- For each input request:
  - `elicitation/create` (form or URL mode): answer `{ action: "decline" }`;
  - `roots/list`, `sampling/createMessage`: not declared, so not answered: the
    server shouldn't have sent them (finding below), and the step ends.
- Retry with `inputResponses` and the echoed `requestState`, for at most 3 rounds.
- Every elicitation is declined (decision 3: `decline` exercises the server's "no" path).
  `--elicitation cancel` is there for a server that treats the two differently.
- Later, if the corpus asks for it: `--elicitation-values <file>` to `accept` with
  fixed values, which is still deterministic.
- `-32021` is read by its code, not its words: a setup failure (`client`), with
  `requiredCapabilities` in the detail. The words-based `client` class from
  `fix/startup-diagnostics` stays, for 2025 servers.
- The step record gains `rounds` and `inputKinds` (form, URL, roots, sampling), and
  `--json` keeps each round's `resultType`.

**Rules** (all `since: 2026-07-28`):

| id | sev | when |
|---|---|---|
| `session/input-required` | info | A tool asked for input. Says which kind, how many rounds, and what the decline led to (completed, tool error) |
| `session/input-loop` | warn | After a decline, the tool asks for the same input again until the round limit: an agent that declines is stuck |
| `session/decline-fails` | warn | A decline makes the tool answer with a JSON-RPC error or end the connection, not a result the model can read |
| `session/undeclared-input` | warn | The server asked for something the request didn't declare (roots, sampling, an unsupported elicitation mode) instead of returning `-32021` |
| `session/result-type` | error | A 2026-07-28 result without `resultType` (MUST). Checked on `tools/call` results; `tools/list` is covered by `spec/schema` (verify) |

**`--auto`.** Elicitation tools are rarely marked read-only, so `--auto` mostly won't
call them. They're covered by scenarios and by the fixture. A read-only tool that
asks for input is called as usual.

**Tests.**
- New `test/fixtures/mrtr-server.mjs`: a 2026 SDK server with one tool for each
  outcome: completes after a decline; loops; errors on a decline; sends `roots/list`
  undeclared; returns `-32021`.
- One raw-stdio fixture that leaves out `resultType` (the SDK always adds it).

**Corpus check.** `server-everything`'s `trigger-elicitation-request`,
`trigger-multi-step-elicitation` and `trigger-url-elicitation`, through a scenario.
Expected result: `session/input-required` only, nothing at warn or above.

**Risk.** The SDK API for `allowInputRequired` and per-request capabilities must be
confirmed against `@modelcontextprotocol/client` 2.1 before design is final. Its
typings mention both; pin the version that works.

## 2. `x-mcp-header`: tools HTTP clients must hide

**Problem.** A parameter can carry `x-mcp-header`, so its value is mirrored into an
`Mcp-Param-{name}` HTTP header. "Clients using the Streamable HTTP transport **MUST**
reject tool definitions where any `x-mcp-header` value violates these constraints.
Rejection means the client **MUST** exclude the invalid tool from the result of
`tools/list`" (`server/tools.mdx`). So one bad annotation makes the tool vanish in
compliant clients, and the server's author sees no error.

**The constraints** (`server/tools.mdx`, `basic/transports/streamable-http.mdx`):
- not empty;
- HTTP field-name token syntax (`1*tchar`, RFC 9110 §5.1), no control characters;
- case-insensitively unique within the tool's `inputSchema`;
- only on `string`, `integer` or `boolean` (never `number`); a `const`/`enum`/default
  integer within ±(2^53−1);
- statically reachable: a chain of `properties` keys only, never through `items`,
  `oneOf`/`anyOf`/`allOf`/`not`, `if`/`then`/`else` or `$ref`.

**Rule.** `spec/x-mcp-header`, `since: 2026-07-28`. Severity: **error** on an HTTP
server; **warn** on stdio, where clients "MAY ignore" it but the same server is often
also deployed over HTTP. The message names the tool, the parameter path, the broken
constraint, and: "Streamable HTTP clients must leave this tool out of their menu."

**`diff`.** An `x-mcp-header` added, removed or renamed is `diff/x-mcp-header`
(info): proxies and WAFs that route on the header see the change.

**Tests.** One fixture per constraint. `server-everything`'s valid `get-header-params`
is the negative control: it must produce no finding.

## 3. `$ref` that clients won't follow

**Problem.** Schemas may now use any JSON Schema 2020-12 keyword (SEP-2106).
"Implementations **MUST NOT** automatically dereference `$ref` values that resolve to
a network URI", and "Schemas that fail to validate due to an unresolved external
`$ref` **SHOULD** be rejected" (`basic/index.mdx`, `$ref` Resolution). A tool whose
schema depends on `https://…/schema.json` is broken or dropped in a compliant client.

**Rule.** `spec/ref`, `since: 2026-07-28`:
- a `$ref` to a network URI: **error** (clients won't fetch it);
- a local `$ref` (`#/...`) that doesn't resolve within the tool's own schema:
  **error**. A tool's schema can't reach another tool's `$defs`.

**Before building:**
- Read the composition-keyword resource bounds in SEP-2106 / `basic/index.mdx`. If
  they set numeric limits (depth, count), check them too. If they're implementation
  choices, leave them out.
- Run the dangling-`$ref` check over the corpus's 788 local `$ref`s first. Today:
  0 network `$ref`s in 144 menus.

## 4. Server-minted handles (SEP-2567)

**Problem.** Sessions are gone. Servers that need state across calls hand out handles
as ordinary tool arguments (`basket_id`). The spec's guidance (`server/tools.mdx`):
- state the handle's retention "in the creation tool's description" ("baskets expire
  after 24 hours of inactivity");
- "a call against an expired or unknown handle should return a tool execution error
  that says so, so the model can recover by creating a new one."

**Rules.**
- `ids/handle-lifetime` (info, unsure, `since: 2026-07-28`, `snapshot`). A tool that
  creates a handle, but whose description says nothing about how long it lasts. A
  creation tool is a `create`/`start`/`open` verb whose output, or whose matching
  `ids/authored` parameter, is a handle-like ID (session, basket, cart, draft,
  handle, job, run). The corpus has 102 handle-like parameters and 72 descriptions
  that state a lifetime, so tune for precision there first.
- `session/handle-error` (warn, unsure, `since: 2026-07-28`). `--auto` already calls
  read-only tools with made-up IDs. When the argument is a handle, a JSON-RPC error
  in reply (`-32602` or other) means the model gets no readable reason. The spec asks
  for a tool execution error (`isError: true`) instead.

## 5. Menus that vary by credentials

**Problem.** The tool set "**MAY** vary by the authorization presented on the
request" (`server/tools.mdx`), and toolmenu sees only one credential's menu.
`cacheScope: "public"` lets shared caches serve a list "across authorization
contexts", which is wrong if the list depends on who asks.

**Design.**
- `snapshot --as <name> <credentials>` (repeatable), and in the config:
  `identities: { reader: { headers | env }, admin: { … } }`.
- Lists the menu once per identity; the first one is the main menu file.
- Output: per identity, the tools it adds or lacks against the main one, and token
  totals.

**Rules.**
- `menu/auth-variance` (info): the menu differs between identities. Allowed; it says
  what differs, so a baseline per identity can be committed.
- `spec/cache-scope-public` (warn, `since: 2026-07-28`): the menu differs between
  identities and is marked `cacheScope: "public"`. This narrows today's `spec/cache-hints`
  info into a finding with evidence.

**Note.** On stdio, an identity is an env set. The fresh-process probe already exists
(`probe.ts`), so this is a loop around it.

## 6. Client profiles

**Problem.** What an agent sees depends on the client. The description cut (Claude
Code: 2,048 characters) is in toolmenu now, but these aren't:
- **whether the client defers tools.** Under Claude's tool search the up-front cost
  is close to zero and each tool costs its size when loaded; Claude Code lists
  deferred tools by name only;
- **the search limit** (5 by default);
- **name limits.**

So the headline token count over-states cost for deferring clients (editmamei:
~38.5K "up front").

**Design.**
- `--client <name>` (config `client`).
- Profiles live in `src/clients.json`, one object per client, and **every value
  carries its source URL and the date it was read**. A value nobody has sourced is
  not shipped.
- First profiles: `generic` (today's behaviour), `claude-code`, `claude-api-search`.
- Output for a deferring profile: "Up front: ~N tokens (search tool + K non-deferred
  tools, or names only). On demand: ~M per tool loaded, largest X." Plus which 3–5
  tools to keep non-deferred (the docs' advice), picked by size and by
  `routes.yml`.
- `search/findable` (on `feat/search-findable`) runs for deferring profiles, and on
  `generic` only above its size threshold.

**Verify before shipping.** Claude Code's deferral behaviour and threshold, from its
docs, not from inside a session. Tool-name limits per client.

## 7. OpenAI `tool_search`

**Problem.** The Responses API has a `tool_search` tool, `defer_loading: true` on
functions inside a **namespace** and on MCP server tools, and hosted or
client-run search. What the model sees before searching, and which fields are
searched, decide how `search/findable` should rank for it.

**Sources.** OpenAI's API spec, `openai/openai-openapi` (`openapi.yaml`:
`tool_search_call`, `defer_loading`, `NamespaceToolParam`), and the SDKs' tests
(`openai-node` `tests/helpers/responses-function-defer-loading.test.ts`) give the
request and response shapes. Both are on GitHub, so no extra network access is
needed.

Ranking behaviour may only be in OpenAI's prose guide: what the model sees before
searching, which fields are searched, and how many results come back. If the spec
doesn't settle these, the `openai-search` profile (point 6) ships with the values it
does settle and leaves the rest out, per point 6's sourcing rule. `search/findable`
adapts if namespaces change what's searched.

## 8. Prompts and resources lists (in scope: decision 4)

`prompts/list`, `resources/list` and `resources/templates/list` are cacheable results
too (`ttlMs`/`cacheScope` required, SEP-2549), and they also "no longer vary
per-connection" (changelog major 1). Clients load them alongside tools. The same
checks would apply: determinism, process/connection variance, cache hints, schema.

**Design:**
- `snapshot --lists tools,prompts,resources` (default `tools`);
- optional `prompts` and `resources` keys in the menu file (additive: still
  `toolmenu: 1`; older readers ignore them);
- the variance rules generalized over list kinds;
- `diff` for them in a later release.

This widens toolmenu from the *tool* menu to everything a client loads up front.
SPEC §1 and the README say so when it ships.

  corpus hit checked by hand (0.8 principle).

## 10. Decisions

1. **Identity rule (SPEC §1): amended.** A rule also earns its place when a
   2026-07-28 MUST makes compliant clients hide, reject or misread part of the menu.
2. **Rules with no corpus case yet: ship, with tests that show the behaviour end to
   end** (§0).
3. **Elicitation answer: `decline`.**
4. **Prompts and resources: in scope** (point 8).
5. **Network access: not needed.** OpenAI's API spec and SDKs are on GitHub (§7). A
   scan of remote servers is optional, from any machine that can reach them.
